# 12 周学习路线（v2：按招聘要求校准）

更新：2026-11-02。学习者：有 React/TypeScript 与金融支付业务经验的前端工程师。

## 目标与取舍

主线：**Web3 支付产品全栈**。发挥前端与支付经验，补齐 EVM/合约、钱包交互、后端 API、数据库、链上同步与工程交付。

依据：[四家公司 8 个工程岗位的证据与能力矩阵](../06-company-research/2026-11-02-hiring-requirements.md)。其中 Coinbase Payment Acceptance 与项目最贴近；各公司岗位有差异，不把相邻前端、后端、协议岗位要求合并成一个虚构的“全栈岗”。

12 周交付基础能力和可验证作品集，不承诺达到资深岗位的生产经验门槛。保留每天 1～2 小时，按每周约 10 小时、总约 120 小时规划；按掌握程度延长。课程只展开当前任务，当前仍是第 1 天。

- P0：本轮必做，保持最小可运行闭环。
- P1：时间允许才扩展，不阻碍核心验收。
- P2：结业后专项，不挤入当前 12 周。

原版已保留在 [v1 快照](revisions/ROADMAP-2026-11-02-v1.md)。

## 五阶段安排

| 阶段 / 周数 / 建议预算 | 核心学习内容 | 实战和通过门槛 |
| --- | --- | --- |
| 1 / 第 1～2 周 / 16h | 区块、交易、回执、公私钥与地址、钱包、消息/交易签名、Gas、EVM、合约、ERC-20、Ethereum/L2；RPC、ABI/log 基础与 viem 读取；理解订单与支付记录模型 | 分析真实测试链交易并与浏览器核对；用自己的话解释提交/执行/确认；识别链、金额单位、目标合约；画出订单与链上支付关系，暂不建完整后端 |
| 2 / 第 3～4 周 / 20h | Solidity 类型、函数可见性、view/pure/payable、modifier、mapping/struct/array、event/error/require、继承、interface/library、ERC-20、OpenZeppelin；从首次合约开始接触基础测试 | 计数器 → 简单资金管理 → 测试 ERC-20 → 最小支付事件；转账/授权/transferFrom；独立解释权限、资金流、回退与整数精度，基础用例通过 |
| 3 / 第 5～6 周 / 20h | Forge/Cast/Anvil、编译部署调试、单测/fuzz/invariant、重入/权限/精度/Oracle 风险/CEI；第 6 周拨约 4h 做 Node/TS 薄 API 与 PostgreSQL schema/迁移/唯一约束/事务入门 | ERC-20 安全测试、漏洞复现修复；本地订单 create/query API，覆盖参数错误、重复键和商户隔离；避免等到第 9 周才首次接触数据库 |
| 4 / 第 7～8 周 / 24h | React + wagmi/viem、钱包连接、链 ID、读写/授权/签名、状态监听、事件/RPC；TanStack Query 查询键、缓存失效、账户/网络切换；异常 UX、可访问性、性能与关键路径测试 | 收银台雏形：余额/授权/支付/交易反馈；测试拒签、错链、失败、重复点击、切换账户及旧缓存；P1 提取薄 TS SDK，不重教 React 语法 |
| 5 / 第 9～12 周 / 40h | 支付网关 M1～M4：React/TS/Vite + Solidity/Foundry + Node/TS/PostgreSQL；同步与恢复、对账、日志、CI、文档 | 逐个通过下表里程碑；核心范围只做单测试链、单测试 ERC-20、一次性支付；能从干净环境复现并演示异常与恢复 |

阶段预算含练习、复习和验收，不是只读教程的时间。若阶段 3 的后端入门或阶段 5 的恢复测试超过预算，延长当前阶段，先去掉 P1；不删掉安全/事务测试来凑日期。

## 支付网关里程碑

项目名：Web3 Merchant Payment Gateway。各周约 10h，按实际验收推进。

| 里程碑 | P0 交付范围 | 验收证据 |
| --- | --- | --- |
| M1 / 第 9 周 | 复用第 6 周 API 骨架；商户、订单、支付尝试、链上事件与同步游标模型；订单号/chain/token/amount/收款方绑定；商户身份与数据隔离；超时/迟到支付策略；OpenAPI 和迁移 | 两个测试商户不能互查/修改订单；重复创建请求不产生重复业务订单；金额为整数最小单位；写出合约参数防篡改与资金路径设计；API/schema 测试通过 |
| M2 / 第 10 周 | 支付合约与测试代币；收银台钱包、授权与付款；事件关联订单；防重付/越权；交易失败反馈；链上收款和订单状态分离 | Foundry 成功/失败/边界测试、API 与本地链集成；验证错误代币/金额/商户和重复支付；端到端核心路径；测试环境内验证商户实际收到预期代币 |
| M3 / 第 11 周 | 一个可独立重启的同步 worker；持久化游标、范围补扫、确认策略、区块身份检查和重组恢复；chainId/txHash/logIndex 去重并跟踪规范链身份；重试/退避；订单/支付记录对账 | 重复事件不重复入账；处理事件和更新游标保持事务一致；在本地链模拟回滚后失效旧事件并重算订单；停止/重启可补齐；RPC 临时失败后恢复；产生不一致清单，保留演练记录 |
| M4 / 第 12 周 | 商户交易记录、状态查询、交易哈希和浏览器链接；结构化日志/traceId、同步滞后与失败计数；CI、可复现启动、运行手册和英文 README 摘要 | 至少一次本地端到端演示与测试网正常付款演示；拒签/错链/执行失败/超时/重复/重组/恢复证据；能根据日志定位预设故障；写出一个项目级 SLI/SLO 目标及本地测量，不冒称生产 SLA |

必须通过当前里程碑再进入下一个。支付成功需要核验合约、事件、订单、链、金额、代币、收款方与确认策略。重组可能改变此前观察到的结果，不能只依赖“收到回调”或“status 成功”。

Node/REST + 数据库驱动 worker 是当前教学实现，目的是理解边界与恢复。它不等价于招聘方要求的 Go/gRPC/Temporal 生产经验；项目 README 必须列出这一差距。

## 工程能力贯穿方式

- **测试**：合约关键路径与安全性质；API 参数/权限/事务；前端交易状态和缓存；少量关键 E2E。测试工具在对应阶段核对版本后选型，不为无关样式改动写镜像测试。
- **数据库**：PostgreSQL 为教学选择；关注迁移、唯一约束、原子更新、并发和查询，ORM 不是学习目标。
- **前端质量**：关注链上数据陈旧、切换链/账户、授权与支付状态分离、可访问性和加载/失败状态；Vite 保留，Next.js 放到 P2，避免同时迁移框架。
- **交付**：第 3 周起每阶段留下一个小而完整的代码变更、测试证据和设计说明；项目阶段接入 CI 与结构化日志；本地可用容器运行数据库，云部署为 P1，不开通付费服务。
- **源码阅读**：阶段 2 读 OpenZeppelin ERC-20/权限；阶段 3 追一条测试路径；阶段 4 追 wagmi/viem 的一次调用与缓存路径；阶段 5 读一条稳定币支付或 SDK 集成路径。届时核实官方仓库/版本，保存链接、模块、调用链和测试说明，不预填阅读完成。
- **表达与 AI**：每阶段写一小段英文技术说明；能解释设计取舍、失败场景和人工验证过程。AI 生成的代码必须能讲解并验证，不能当成独立完成的证明。

## 范围管理

P0 不做多链支付、订阅、真实资产兑换或自建托管。P1 可选薄 TypeScript SDK、经过充分测试的 webhook 重试、只读 AMM 报价或测试环境云演示，最多选一个小扩展。

P2：Go 并发/测试 + gRPC、用 Temporal 复写一个工作流、Next.js、React Native、Chainlink Data Feeds/CCIP、AMM/滑点/MEV 与 Uniswap 协议源码、复杂 Solidity 数学和系统安全。退款/资金托管/真实结算另开设计与安全评审。按目标岗位选分支，不要求全部同时掌握。

只用测试币、测试网和本地链；资深岗位的主网经验要求不能成为使用真实资金的理由。

## 验收与进度管理

学习者的知识点状态只随练习/测试证据变化。更新课程不是完成课程。每次结束追加日志并更新进度、知识关系和真实错题；必要练习未通过不结项。

每阶段开始前，在当前会话复核相关官方 JD 后再决定是否微调；记录日期和证据，区分硬要求、优先项及教学推导。不创建后台定时抓取。

求职准备同时记录岗位年限、地区/工作许可、英语、生产经验和作品集证据。四家公司的样本多为资深或特定地区岗位；12 周后评估真实差距，再决定延长训练或投递方向。
